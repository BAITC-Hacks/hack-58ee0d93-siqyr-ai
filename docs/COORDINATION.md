# Согласование работы трёх участников

Цель — продолжить уже начатую работу, соединить части и избежать конфликтующих правок. Это документация; задания другим Codex-задачам автоматически не отправлены.

## Владельцы файлов

| Участник | Единолично редактирует | Изменение чужой области |
|---|---|---|
| Meiirlan | backend/app/, backend/shared/, backend/requirements.txt, root config/locks, scripts/, tests/, общий CONTRACT/STATUS/DECISIONS | Запрос владельцу frontend или AI, без параллельной правки |
| Nurdaulet | frontend/ целиком, включая AGENTS, package-lock и внутренние типы | Запрос Meiirlan для API/schema; запрос Alibi через Meiirlan, если меняется AI-формат |
| Alibi | backend/stt/, backend/agents/, backend/requirements-stt.txt, evaluation/, eval/, data/synthetic/ | Запрос Meiirlan на transport/config/shared schemas |

Промпты в prompts.md отражают проверенный frontend из main: React/Mantine/Dexie/npm уже выбраны. Не навязывать прежний CSS-only план. Нурдаулет выбирает внутренние UI-решения на основе своего текущего контекста; контракт с backend согласует с Meiirlan. Существующие локальные изменения всегда сначала изучаются, а не стираются ради выравнивания.

## Как обмениваться сообщениями

Разные задачи/ноутбуки не видят незакоммиченные изменения и не получают сообщения из markdown автоматически. Выбрать один уже используемый общий чат команды. Каждый участник сам переносит туда короткий handoff; агент может подготовить его в ответе. Эта инструкция не отправляет сообщения за участников.

Каждый заводит только свой файл:
- docs/handoffs/meiirlan.md
- docs/handoffs/nurdaulet.md
- docs/handoffs/alibi.md

Сейчас это зарезервированные пути будущей работы, не уже опубликованные отчёты. Общие STATUS/DECISIONS сводит Meiirlan. Так участники не правят одну строку одновременно. Когда нужно поделиться кодом — коммит/ветка, когда согласовать незавершённую идею — сообщение с минимальным примером. Локальный markdown становится доступным коллегам только после выбранного способа передачи.

Шаблон:

```text
READY | Nurdaulet | frontend@<реальный SHA> | contract=<SHA контракта>
Готово: adapter upload + отображение статусов.
Проверено: npm run build; mock upload → review.
Нужно от Meiirlan: URL API, origin/CORS, ответ approve с revision.
Не проверено: реальный STT, диаризация.
```

Для блокировки: `BLOCKED | владелец | что ожидал | что получил | один конкретный запрос`.
Для изменения: `REQUEST_CHANGE | поле/route | зачем | пример до/после | кто потребитель | совместимый переход`.
Ответ потребителя: `ACK | изменение | версия | когда мой adapter готов` или `COUNTERPROPOSAL | более дешёвое решение`.

Не заполнять SHA выдуманным значением. Пока нет коммита, писать `uncommitted; передано примером`. ACK — реальное подтверждение коллеги, не предположение агента.

## Первый обмен и порядок интеграции

1. **Все → Meiirlan:** текущая ветка/коммит, что уже готово, какие файлы заняты, один blocker. Нурдаулету не поручать заново создавать готовые экраны.
2. **Meiirlan → оба:** один минимальный контракт и synthetic fixture; состояния, ошибки, upload, timed segments, evidence, save/approve. Пометить версию, реализовано ли это или только предлагается. Локальный проект v0.2 не навязывать как действующий main.
3. **Alibi → Meiirlan:** сигнатуры модулей, зависимости и smoke output. **Нурдаулет → Meiirlan:** подтверждение adapter и необходимые поля. Внутренние UI-типы могут отличаться от API — это решает adapter.
4. **Meiirlan:** публикует mock API; Nurdaulet проверяет один путь. Alibi подключается через те же интерфейсы, без изменений экранов.
5. **Совместно:** один новый аудиофайл → реальные timed segments → поручения → ручная правка → server approval → экспорт утверждённых данных. Отдельно отмечать, где пока mock.

Статус — после каждого законченного блока (примерно 20–30 минут), blocker сразу. Если проблема не решена за 10–15 минут, участники созваниваются на 3 минуты и сокращают scope. Это рабочая договорённость, не настроенная автоматизация.

## Контракт и экспорт

Meiirlan единственный вносит согласованные изменения CONTRACT/shared schemas. Существующие поля не переименовывать сразу: сначала совместимое добавление и adapter, затем миграция после ACK. Каждый READY указывает версию контрактного коммита и что проверял потребитель.

Нурдаулет сохраняет актуальный UI, IndexedDB для локальных черновиков и готовый экспорт. Предпочтение для MVP: сервер сохраняет immutable approved snapshot; frontend генерирует имеющийся DOCX/печать PDF именно из него, только после approval. Это предложение экономии времени, требует короткого ACK Meiirlan и Nurdaulet. Если серверный export уже готов — использовать его, не переписывать заново. После решения Meiirlan обновляет контракт и указывает не реализуемые пока file endpoints. Одновременная разработка двух разных экспортных путей запрещена без конкретной причины.

## Git без столкновений

- Каждый продолжает свою существующую ветку в отдельном checkout/клоне. В новом checkout использовать codex/ префикс; не переименовывать уже рабочие ai/frontend ветки.
- Если три агента работают на одном компьютере, нужны отдельные worktree/checkout; три ветки в одной общей рабочей папке не изолируют правки.
- Перед синхронизацией проверить git status. Незавершённые изменения сначала безопасно сохранить с участием их владельца. Без reset --hard, force-push и переключения чужой ветки.
- Небольшой PR/коммит включает только свои файлы. Не git add -A на дереве с исходными записями/секретами. Ключи, .env, БД и веса не коммитить.
- Meiirlan последовательно интегрирует готовые изменения в main. Общие файлы при конфликте разрешает с владельцем; не выбирать автоматически ours/theirs.
- После merge каждый синхронизирует свою ветку на чистом состоянии и повторяет свою короткую проверку. Одна успешная сборка frontend не доказывает E2E.

## Что передать коллегам сейчас

Три блока prompts.md вставить в существующие Codex-задачи каждого участника. Нурдаулету — именно блок продолжения, без перезапуска задачи. Полный план из нашей текущей рабочей копии ещё не находится в main; не ожидать, что другие задачи его уже прочитали. При расхождении со старым планом фиксировать реальный работающий код и минимальное согласованное изменение, а не откатывать прогресс.
