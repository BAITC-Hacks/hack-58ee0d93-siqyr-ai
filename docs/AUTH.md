# Авторизация для демо и корпоративного контура

## Запуск локального демо

В `.env` задайте `AUTH_MODE=local`, случайный `JWT_SECRET` длиной от 32 символов, `BOOTSTRAP_ADMIN_USER` и `BOOTSTRAP_ADMIN_PASSWORD` длиной от 12 символов. Администратор создаётся один раз при первом запуске; существующий пароль при перезапуске не меняется. После первого запуска удалите bootstrap-пароль из окружения. Не коммитьте `.env`.

`POST /api/auth/login` с `{ "username": "...", "password": "..." }` возвращает короткоживущий Bearer JWT. Передавайте его в `Authorization` всех рабочих запросов. Для запуска `scripts/demo_e2e.py` можно задать `DEMO_USER` и `DEMO_PASSWORD` либо оставить bootstrap-переменные на время локального показа. `AUTH_MODE=disabled` сейчас используется для показа без входа; для рабочего развёртывания выберите `local`, `hybrid` или `keycloak`.

Для личного кабинета используйте `GET /api/profile`. `PATCH /api/profile` меняет отображаемое имя, язык (`ru`, `kk`, `en`), тему (`system`, `light`, `dark`) и локальное предпочтение уведомлений. Последнее хранится в профиле и пока не меняет фоновую рассылку напоминаний. `PUT /api/profile/avatar` принимает JPEG/PNG/WebP до 2 МБ и приводит изображение к WebP 256×256 без EXIF. `GET /api/profile/avatar` возвращает файл только владельцу токена, `DELETE` удаляет его. В режиме демо без входа профиль доступен только для чтения.

`POST /api/profile/password` требует текущий и новый пароль длиной от 12 символов, отдаёт новый access token и отзывает все старые локальные токены пользователя. При корпоративном входе через Keycloak пароль меняется в Keycloak, а не в приложении.

Системный администратор добавляет департаменты, пользователей и роли через `/api/admin/*`. Идентификаторы департаментов стабильны, например `finance` и `legal`. Создание совещания принимает `department_id`; все связанные файлы, события, поручения и уведомления видны только участникам этого департамента. `department_admin` действует только в назначенном департаменте; вложенные департаменты не наследуют права автоматически.

## Подключение Keycloak Самрук-Казына

Для демонстрации готовности достаточно показать три режима: `local`, `hybrid` (локальные и корпоративные токены) и `keycloak` (парольный вход отключён). После получения реквизитов от ИТ заказчика заполните `KEYCLOAK_ISSUER` полным HTTPS URL realm, `KEYCLOAK_AUDIENCE` ожидаемым `aud` access token и выберите режим. API проверяет подпись RS256 через JWKS realm, `iss`, `aud`, срок действия и локальную активность пользователя. Непривязанный `sub` не получает доступ.

Для каждого сотрудника создайте локального пользователя, назначьте ему membership и свяжите с `sub` через `/api/admin/identities` (`provider=keycloak`). Логин и пароль такому пользователю не нужны. Это позволяет начать пилот до согласования корпоративных групп и не даёт внешнему claim автоматически выдать права администратора. После получения схемы групп можно добавить синхронизацию membership с правилами заказчика. Для браузерного входа рекомендуем Keycloak Authorization Code с PKCE; UI должен получить access token и передавать его API. Backend не принимает ID token вместо access token.

Заказчик должен сообщить: URL realm внутри закрытого контура, client ID и ожидаемую audience, алгоритм подписи, claim `sub`, список групп/ролей и правила сопоставления департаментов, требования к выходу/отзыву токенов и разрешённые redirect URI. Корпоративный адрес Keycloak и JWKS должны быть доступны backend внутри контура.

## NCALayer и ЭЦП

NCALayer работает на компьютере пользователя и подписывает данные в браузере. UI вызывает `/api/auth/ecp/challenge`, получает `data_base64` и просит NCALayer создать CMS-подпись **точно этих байтов**, затем отправляет CMS и `challenge_id` в `/api/auth/ecp/verify`. Подписывать можно через модуль `kz.gov.pki.knca.basics`; формат CMS (attached/detached) фиксируется вместе с выбранным серверным проверяющим сервисом.

Сам backend не считает ответ NCALayer доказательством личности. `ECP_VERIFY_URL` должен указывать на доверенный внутренний сервис, который получает `{cms, payload}`, проверяет криптографическую подпись, цепочку и срок сертификата НУЦ РК, статус отзыва и возвращает JSON:

```json
{"valid": true, "certificate_valid": true, "revocation_checked": true, "payload": "siqyr-ai:login:...", "subject": "устойчивый-идентификатор-сертификата-или-владельца"}
```

`payload` обязан совпасть с challenge побайтно. `subject` заранее привязывается к локальному пользователю через `/api/admin/identities` (`provider=ecp`). Challenge действует 3 минуты и используется один раз. При пустом `ECP_VERIFY_URL`, ошибке проверки или неизвестном `subject` вход закрыт. Не направляйте CMS, персональные данные и аудио во внешний сервис. Заказчик должен согласовать внутренний проверяющий сервис, политику отзыва, идентификатор владельца и сертификаты доверия.

У браузерного `EventSource` нет поддержки заголовка Bearer. Для `/api/runs/{id}/events` используйте `fetch` с `Authorization` и потоковый разбор SSE; формат событий не меняется.

Источники по интеграции: [Keycloak OIDC endpoints и JWKS](https://www.keycloak.org/securing-apps/oidc-layers), [Keycloak Authorization Code и PKCE](https://www.keycloak.org/docs/latest/server_admin/), [официальный NCALayer НУЦ РК](https://ncl.pki.gov.kz/).
